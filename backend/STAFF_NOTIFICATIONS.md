# Медосмотры, дни рождения и проверка расписания

## Сотрудники

Закрытая страница `/admin/schedule/staff-dates`: медосмотры, ближайшие дни рождения,
получатели VK. Доступ только admin/superadmin. Даты хранятся отдельно в
`staff_dates`; публичные модели преподавателя/пользователя их не содержат.
Преподаватель — основная запись, связанные учётные записи не дублируются.
Несвязанные employee-аккаунты (teacher/admin/superadmin) также присутствуют.
Если позже связывается учётная запись с преподавателем, даты не объединяются
автоматически: проверить и при необходимости заполнить карточку преподавателя.

API `/api/admin`:

- GET `/staff-dates` — список, рассчитанные календарные сроки, часовой пояс.
- PUT `/staff-dates/:kind/:id` — `revision`, `birth_date`, `medical_until`;
  kind = teacher/user, даты YYYY-MM-DD или null. Revision=0 только для новой записи.
- GET `/staff-reminder-recipients` — существующие страницы VK и независимые флаги.
- PUT `/staff-reminder-recipients/:id` — `revision`, `medical`, `birthdays`.

Таблицы `staff_dates`, `staff_reminder_preferences`, `staff_reminder_deliveries`
добавляются существующей локальной миграцией GORM: date-колонки, внешние ключи,
уникальные владельцы/события, CHECK единственного владельца и положительной revision.
Старые даты не придумываются. Конкурирующее редактирование возвращает 409.

Отправка в 09:00 Asia/Yekaterinburg, независимо от TZ сервера. Флаги новых
напоминаний изначально выключены. Дополнительно учитывается общий IsEnabled
получателя VK; глобальная административная рассылка не включает эти уведомления
автоматически. Неактивным/архивным сотрудникам напоминания не формируются.

Медосмотр: за 20 дней и в день окончания. Если задание/сеть были недоступны,
предварительное сообщение догоняется в оставшиеся 1–20 дней, один раз получателю.
День рождения: за 2 дня, при сбое допускается догоняющая отправка за 1 день.
В сам день/после дня рождения старое сообщение не отправляется.
29 февраля в невисокосном году считается 28 февраля; это явно показано в интерфейсе.

Реестр доставки устойчив к перезапускам. Ошибки повторяются через 5 минут,
успешная отправка отмечается отдельно для каждого получателя и срока.
VK random_id стабилен при повторах; несколько worker сериализуются advisory lock.
Гарантия абсолютного exactly-once при неопределённом ответе внешнего VK не даётся:
дедупликация при таком сбое зависит также от поведения API VK.
В тестах используется подставной sender, реальные сообщения не отправляются.

## Проверка существующей рассылки расписания (код не изменялся)

Что уже предусмотрено:

- 20:00 по Asia/Yekaterinburg: завтра; по субботам — следующая неделя.
- Фильтр утверждённых расписаний; черновые массовые правки не рассылаются.
- Отдельное включение расписания и привязка преподавателя у получателя VK.
- Изменения времени/кабинета/отмены/переноса/удаления и смены преподавателя.
- После реально отправленного вечернего ежедневного сообщения добавляется
  актуальное расписание завтрашнего дня; до него — краткое сообщение.

Обнаруженные ограничения:

1. `RecordSlotChange` сравнивает только дату с today: изменения сегодняшних,
   ещё будущих по времени занятий также пропускаются.
2. `processEvent` не отбрасывает сообщение целиком, когда все его даты уже прошли.
   После длительной недоступности VK устаревшее summary может быть отправлено.
3. `equivalentScheduleSlots` не сравнивает ученика, предмет и группу. Их замена
   при тех же времени/кабинете/преподавателях может остаться без уведомления.
4. Снятие утверждения → правки черновика → повторное утверждение не создаёт
   сводного изменения и не обновляет ранее помеченные отправленными дайджесты.
5. Субботняя недельная рассылка не догоняется в воскресенье, если субботняя
   отправка целиком была пропущена или следующую неделю утвердили позднее.
6. Slot сохраняется раньше outbox: сбой между ними может потерять событие.
   Массовая очистка/перегенерация не использует общий путь уведомления слотов.
7. В существующем создании получателей VK bool-поля с GORM default:true
   могут заменять переданное false на true даже с Select("*"). Выключение
   существующей записи отдельным UPDATE работает; начальное выключенное
   состояние требует отдельной правки и регрессионного теста.

Рекомендуемая следующая доработка: версия публикации расписания, атомарный
outbox внутри транзакции изменения, сравнение всех значимых полей, фильтрация
по времени окончания занятия при доставке; при повторном утверждении — одно
сводное обновление затронутых будущих дней. Черновые правки по-прежнему молчат.
Для уже присланного дня — краткое описание + актуальный день, для отдалённых
изменений — краткое сообщение. Публикация после субботы требует catch-up недели.

Это проверка локального кода, не подтверждение реальной доставки. Production,
реальные получатели в production-БД и реальные отправки VK не проверялись.
