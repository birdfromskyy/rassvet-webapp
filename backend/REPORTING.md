# Месячные социальные услуги — Phase 1

Только backend. Расписание, тарификация преподавателей и Desktop не изменяются.
Все маршруты ниже находятся под `/api/admin`, используют существующие JWT/cookie
и `AdminMiddleware` (admin/superadmin). Родители и преподаватели доступа не имеют.
Паспортов, свидетельств и локальных файлов в новых DTO/таблицах нет.

## Данные и миграция

- `students`: `last_name`, `first_name`, `middle_name`, `birth_date` (DATE),
  `identity_revision`. Прежние ID и `full_name` сохранены. Старые ФИО автоматически
  не разбиваются, даты рождения и юридические связи не угадываются.
- `legal_representatives`: отдельный человек, необязательный `user_id`, revision.
  Удаление аккаунта обнуляет эту связь, не удаляет человека. Архивация через
  `is_active=false`; физическое удаление людей/связей, используемых в месяце,
  ограничено FK. Учётная запись автора истории также защищена от hard delete;
  существующее soft delete пользователей сохраняется.
- `student_legal_representatives`: уникальная пара ребёнок/представитель,
  отношение, необязательные границы полномочий, revision. Отдельно от `user_students`.
- `social_service_report_settings`: единственная запись `id=1`, общие номер/дата
  договора, revision. При миграции реквизиты пустые, не выдумываются.
- `student_service_months`: UNIQUE(student_id, month), DATE первого числа месяца,
  выбранный представитель, draft/finalized, revision, снимок людей/связи/договора,
  авторы/даты. Месяц включает год. FK выбранного представителя проверяет связь
  именно с этим ребёнком. При выборе проверяется действие полномочий на последний
  день месяца. Пустой черновик разрешён.
- `student_service_month_items`: услуги со снимками кода, названия, категории,
  порядка, частоты, максимума, длительности, тарифа. ID сохраняется при редактировании
  позиции. Количество `null` означает «не заполнено», `0` — подтверждённый ноль.
- `student_service_month_revisions`: полный JSONB-снимок каждой редакции,
  schema_version, действие, автор, время. UPDATE/DELETE запрещены триггером.
- `social_service_legacy_migrations`: подтверждённый переход со старого набора.
- `reporting_schema_migrations`: версии, SHA-256 и время применения SQL.

SQL в `internal/database/migrations/reporting/` выполняется после существующих
миграций приложения. Advisory lock и транзакция предотвращают частичное применение;
изменение уже применённого SQL обнаруживается по checksum. Новые изменения схемы
добавлять следующим файлом, не редактировать применённый. Автоматического destructive
down нет. На Phase 1 миграции проверены только в отдельной локальной тестовой БД.

Привязку прежних `StudentSocialService` к месяцу выполняет только явный запрос
`mode=migrate_legacy`. Пока есть старый неперенесённый набор, обычное создание
месяца возвращает 409. Старые строки остаются неизменяемым архивом. Исторические
месяцы не создаются. По умолчанию прежний факт НЕ переносится: даже старый ноль
не доказывает заполнение. `include_legacy_actual=true` явно подтверждает перенос
всех прежних количеств. Неизвестная частота требует `legacy_maximums` по ID услуг.

До перехода прежние endpoints/экран продолжают работать. После первого месячного
набора старый endpoint `/students/:id/social-services` возвращает 409 с
`code=monthly_reporting_required`, чтобы не экспортировать устаревший факт за
произвольный месяц. Триггер блокирует и конкурентную старую запись. UI перехода
появится в Phase 2; сейчас автоматически переводить детей не нужно.

## Расчёты и снимки

Распознаются точные формы `N раз/раза в день/неделю/месяц` без учёта регистра и
повторных пробелов. Недельный множитель 4, дневной временно сохранён 31 (как в старом
проекте), месячный 1. Календарный дневной множитель ещё не согласован. «За курс»,
«по назначению врача», ИППСУ, варианты с «ИЛИ» и иной текст НЕ интерпретируются
по первому числу: нужен явно заданный `maximum_monthly_count`, единица `manual`.
Для распознанной частоты переданный максимум должен совпасть с расчётом.

Границы: до 1000 позиций, максимум 0–100000, длительность 1–1440 минут,
тариф 0–100000000 копеек. Это ограничивает суммы ниже int64. Услуги бесплатные:
стоимость/компенсация = факт × тариф; доплаты нет. Суммы и минуты вычисляются,
не сохраняются как второй источник правды. `totals.unfilled` учитывает null.

Правка справочника не меняет существующие позиции. Копирование предыдущего
календарного месяца сохраняет их снимки/тарифы/частоты (включая архивные услуги),
но сбрасывает весь факт в null. Для нового месяца снимки людей и общего договора
берутся актуальные; представитель по умолчанию предыдущий, можно выбрать другого.
Внутри существующего месяца снимки людей/договора сохраняются, пока не запрошен
`refresh_snapshots=true` либо явно не изменён выбранный представитель.

Фиксация проверяет ФИО/дату рождения ребёнка, непустой набор и заполненность всего
факта; нулевое количество допустимо. Это фиксация месячных данных, не разрешение
печатать юридически готовый Акт. Представитель/договор/локальные документы будут
проверяться отдельно при подготовке Акта; отсутствие сведений, не используемых
общим Отчётом, не блокирует фиксацию его фактов. Для правки finalized нужен reopen:
предыдущий снимок остаётся неизменным, revision увеличивается.

## API

| Метод / путь | Назначение |
| --- | --- |
| POST `/students` | Старый full_name или структурированные ФИО + birth_date |
| PUT `/students/:id/identity` | Полное ФИО/дата рождения; revision = прочитанный identity_revision |
| GET/POST `/legal-representatives` | Список / создание представителя |
| GET/PUT `/legal-representatives/:representativeId` | Просмотр / полная правка или архивация |
| GET `/students/:id/legal-representatives` | Список юридических связей |
| PUT `/students/:id/legal-representatives/:representativeId` | Создание (revision=0) / изменение связи |
| GET/PUT `/social-service-report-settings` | Общий договор |
| GET `/students/:id/service-months` | Список месяцев; необязательный year |
| GET/POST/PUT `/students/:id/service-months/:month` | Чтение / создание / полная правка черновика |
| POST `…/:month/finalize` | Зафиксировать факты |
| POST `…/:month/reopen` | Открыть следующую редакцию |
| POST `…/:month/copy-previous` | Заменить назначения черновика из предыдущего месяца, с проверкой revision |
| GET `…/:month/revisions` | История; необязательный revision для точного снимка |

Списки: limit=1…100 (по умолчанию 100), offset=0…1000000. Представители ищутся по
`q` (ФИО), в списках нет неявного исключения архивных людей/месяцев. Документы
будущего общего Отчёта должны выбирать именно месячные наборы, а не активных детей.
Ответ GET/POST/PUT месяца: `{month, totals}`, ETag содержит revision.

Полные PUT передают revision прочитанной записи. Отсутствие revision — 428,
устаревшая revision — 409. Для новой связи revision=0. Месяц передаётся строго
`YYYY-MM-01`. В месячном PUT обязательны `items` (весь список) и осознанный выбор
`representative_id` (null снимает выбор); пропущенный факт тоже становится null.
Позиции, которых нет в полном списке, удаляются из текущей редакции, но не истории.
Снимки справочника, ID позиций и суммы клиент назначать не может.

Создание месяца:

```json
{
  "request_id": "client-generated-unique-key",
  "mode": "create",
  "representative_id": null,
  "items": [{"social_service_id": 123, "actual_monthly_count": null}]
}
```

Опциональные overrides позиции: `periodicity`, `maximum_monthly_count`,
`standard_duration_minutes`, `tariff_kopecks`. Неизвестные JSON-поля отклоняются,
вход ограничен 1 MiB. Сервер не принимает документы через эти DTO.

Копирование: тот же POST с `mode=copy_previous`, новым request_id, без items.
Перенос: `mode=migrate_legacy`, request_id, `include_legacy_actual` и при необходимости
`legacy_maximums: {"123": 10}`. Пустой/уже перенесённый legacy-набор — 409.
При создании существующий целевой месяц всегда 409: молчаливой замены нет.
Отдельный POST `copy-previous` с `{"revision": N}` заменяет назначения только
существующего черновика после подтверждения в UI. Количества сбрасываются в null,
снимки услуг сохраняются (включая архивные); сведения людей/договора целевого
месяца остаются прежними. Замена транзакционна и записывается в историю.
Повтор одинакового request_id и тела возвращает исходную revision=1 без новых записей;
после retry для актуального состояния перечитать GET. Повтор ключа с другим телом — 409.
Две параллельные правки одной revision: одна проходит, вторая получает 409.
`finalize`/`reopen` принимают только `{"revision": N}`.

DELETE справочника архивирует использованную услугу, в том числе если она осталась
только в прошлой revision. Неиспользованную услугу можно удалить физически.
Старое редактирование full_name сохраняется; при реальной смене строки структурные
части сбрасываются и identity_revision увеличивается. Не пытаться угадать новый split.

## Проверка

Для тестов нужен отдельный локальный PostgreSQL. Harness разрешает только loopback
и имя БД с суффиксом `_test`; `REQUIRE_TEST_DB=1` запрещает молчаливый пропуск.
Реквизиты ниже — только для временного тестового контейнера, не для dev/production.

```bash
REQUIRE_TEST_DB=1 TEST_DB_HOST=127.0.0.1 TEST_DB_PORT=55439 \
TEST_DB_NAME=phase1_v4_test DB_USER=postgres DB_PASSWORD=phase1-local-test \
go test ./... -count=1
```

Тесты используют синтетические данные, транзакции с rollback. Для реальной
конкурентности создаётся отдельная случайная schema в тестовой БД и удаляется
после теста. Не применять эту команду к рабочим базам.

Проверено: `go test ./... -count=1`, `go test -race ./... -count=1`, `go vet ./...`.
Frontend: `npm run build` проходит с прежними предупреждениями. Имеющийся
`App.test.js` не запускается: Jest не разрешает `react-router-dom`; frontend и
его зависимости в Phase 1 не изменялись. Исправление этого старого теста отдельно.

## Phase 2: интерфейс и ручная проверка

Страница `/admin/schedule/social-service-reports` использует месячный API.
Основной компонент `AdminMonthlySocialServices`; редактор, справочник, карточки
людей и общий договор расположены в `frontend/src/pages/monthly-services/`.
Клиент: `monthlyReportingService.js`. Старый незакоммиченный генератор XLSX не
изменялся; новый месячный экран не выдаёт legacy-экспорт за месячный документ.
Генерация документов остаётся отдельным этапом Desktop.

1. Выбрать ребёнка (доступны также архивные и неактивные) и месяц/год.
2. Для legacy-набора подтвердить перенос именно в выбранный месяц; факты
   не переносятся. Для нового набора выбрать услуги по категориям/поиску.
3. Ввести количества: пустое поле — не заполнено, `0` — подтверждённый ноль.
   Проверить максимум, минуты и сумму. Неизвестная периодичность требует
   явного максимума; недельная использует 4 недели, дневная — 31 день.
4. Сохранить, обновить данные, переключить месяц и убедиться в изоляции.
   Проверить копирование декабря в январь: факты пустые, замена черновика
   требует подтверждения, старые редакции сохраняются.
5. В «Ребёнок и представители» заполнить структурированное ФИО/дату рождения,
   создать или выбрать представителя и сохранить связь. Паспортных полей нет.
   Для уже созданного месяца обновить сведения из карточек отдельной кнопкой.
6. Заполнить все факты и зафиксировать месяц, затем открыть для изменений.
   Отсутствие представителя не блокирует фиксацию фактов.
7. Открыть один месяц в двух вкладках: второй save должен показать конфликт,
   не уничтожая введённые значения. Отключить сеть: ошибка также сохраняет ввод.

Проверки Phase 2: 32 профильных Jest-теста, `npm run build`, `go test ./...`,
`go test -race ./...`, `go vet ./...`. Chrome проверен с синтетическими ответами
API на 1440px и 390px; внешние запросы заблокированы. Общий Jest-прогон всё ещё
останавливается на прежнем `App.test.js`; профильные suites проходят.
